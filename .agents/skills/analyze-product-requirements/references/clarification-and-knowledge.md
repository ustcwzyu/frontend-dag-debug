# 澄清、代码事实与合成规则

## 1. 知识库与代码事实

未执行知识检索时明确记录 `not-integrated`/`not-executed`，不得声称“未命中”或模拟记录。

提供代码仓库时只做定向事实搜索：认证、权限、状态枚举、相似能力、字段类型、统一错误结构。事实使用 `CODE-FACT-*`，包含事实、证据位置和需求影响。代码只能回答现状，不能替代用户决定目标需求。

知识或代码与需求冲突时：保留来源证据、生成澄清问题、用户裁决前不选边。

## 2. 决策树式访谈

1. 从 Product Analysis 的推断、问题、输出规范和高风险默认值提取 3–6 个顶层 `BR-*` 分支。
2. 标注分支依赖，从范围、权限、核心流程、数据语义等基础决策开始。
3. 每轮只处理一个主要问题：先给推荐答案和理由，再提问并等待回答。同分支、同依赖链的子项可合并，不相关问题不得换装为一题。
4. 收到回答后重新识别剩余模糊点；仅在它们会影响范围、输出或验收时开启下一轮。
5. 一次助手提问与用户回答记为一轮，总轮数不得超过 3。第 3 轮后仍有 P0/P1 时保持 pending 并阻断 Product Requirement complete；P2 按已记录的默认行为和影响处理。
6. 所有分支解决后，用一段话总结关键决策。

### 回答复核

收到用户回答后，先判断它是否直接覆盖当前问题的关键决策点、是否只有一种合理的产品解释、是否足以写成明确的范围/规则/输出行为/验收结果、是否与原始明确需求或已有决策冲突，以及是否引入新的未定义概念、例外条件或依赖关系。全部满足时才形成最终决策并标记为 confirmed。

任一条件不满足时：

- 保留用户原始回答，`最终决策` 写“未形成”并说明具体模糊点。
- P0/P1 使用 `pending-blocking`；P2 使用 `pending-non-blocking`，同时记录默认行为和未确认影响。
- 下一轮优先继续当前分支，明确指出上一轮回答仍不清晰的部分，并将问题收窄为可直接确认的决策点；不得原样重复问题或跳到其他分支。
- 不得把模型推断、推荐答案或代码现状当作用户确认。

当前问题明确后，再扫描其他未解决问题和本次回答新引入的模糊点。只有会改变范围、权限、核心流程、数据语义、输出行为或验收结果的问题才继续澄清；不影响产品行为的措辞和下游技术细节不消耗澄清轮次。

问题等级：

- P0：改变范围、权限、关键流程、数据语义或验收结果；必须由用户明确确认。
- P1：可以推荐默认值，但必须经用户确认。
- P2：可延后，但必须给出当前默认行为、影响和后续确认入口。

没有问题时跳过交互访谈，不伪造分支、问题或决策标记，但仍生成完整 Clarification 检查记录。

## 3. 合成规则

Product Analysis 冻结不回写。`最终决策` 是合成最终需求的规范化事实；`目标位置` 指向需求范围、业务规则、故事、输出规范或 AC。

三个产物必须写入同一 `<project-root>/docs/product-analysis/<requirement-id>/`。同目录来源使用相对路径，避免把个人机器绝对路径写入可交接产物。

生成 Product Requirement 时：

- 用户确认的推断转为正式需求。
- 用户否定的推断删除或进入非目标。
- 确认的默认值进入规则和故事。
- 代码库事实只用于解释现状、识别冲突和支持澄清，不作为独立需求来源；未经用户确认且未被原始需求明确要求的代码现状不得进入 Product Requirement。
- 需要合并的代码事实必须转换为目标产品语言，只保留用户可感知的行为、业务规则和验收结果；`CODE-FACT-*`、证据路径、代码符号、模块结构、数据表和实现过程继续留在 Product Analysis 或 Clarification。
- 决策影响故事时重新生成故事与 AC，不只在决策列表堆积答案。
- `DEC-Q-*` 在决策追溯中登记，并能定位到正式章节。
- 无需澄清时不生成任何 `DEC-Q-*`，说明需求直接来源于原始需求。
